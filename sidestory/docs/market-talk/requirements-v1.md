# ICG Facebook 시장·캐릭터 토크 요구사항 정의서

- 문서 버전: 1.0 / 작성일: 2026-10-06 KST
- 대상: `yumens2-byte/investment-comic-gemini`
- 상태: 분석·설계 산출물. 개발·DB 변경·운영 배포·게시 실행 없음.
- 검토 방식: 콘텐츠 편집장, 플랫폼/API 정책 담당, 백엔드 운영 아키텍트의 **3개 AI 역할 독립 검토 및 의견 통합**. 실제 외부 인사 회의나 Meta 승인 결과가 아니다.

## 1. 결론과 목적

기존 캐릭터 설정과 시장 데이터를 활용해 Facebook Page에 짧은 시장 관찰·금융 개념·에피소드 해설을 정기 발행하는 기능을 추가한다. 기능명은 `Market Talk`로 제안한다.

목표는 **검증된 새 소재를 낮은 제작비로 지속 발행**하는 것이다. ‘봇으로 인식되지 않을 최대 발행량’은 확인 가능한 요구사항이 아니다. 공식 API 허용량과 스팸 정책은 서로 다르며, 어느 발행 간격도 차단 방지를 보장하지 않는다. 사람처럼 보이기 위한 랜덤 동작, 계정/IP 교체, 차단 우회는 구현 범위에서 제외한다.

Facebook·Threads를 총비용 무료로 가정하지 않는다. 이번 조사에서는 최신 공식 과금 조건을 확정하지 못했다. 게시 API 비용과 별도로 LLM·시장데이터·실행환경·보관 비용이 발생할 수 있다. X 가격 비교나 기존 X 정책 변경은 이번 범위가 아니다.

### 2.2 첨부 자료

첨부 ZIP 루트는 `investment-os-main/`이며 대상 저장소와 명칭이 다르다. 캐릭터·시장 분석 구조의 보조자료로만 취급하고 최신 카논이나 운영 소스 기준으로 삼지 않는다. Kotlin 5개 파일은 DSL/RSS 수집 학습 예제로 Facebook 게시 구현 근거가 아니다. `BlogPostUpg.kt`의 새 글 조건이 `newFeeds.isEmpty()`이고 실제 대기는 1초로 주석과 다르며, `RunBlocking.kt`의 반복문은 주석 처리되어 있다. 이 예제들을 운영 스케줄러로 재사용하지 않는다.

### 2.3 공식 정책 조사

Meta 공식 발표는 스팸성 도배·배포/참여 조작에 대한 노출·수익화 제한을 설명한다. 무관한 캡션과 과도한 해시태그도 제한 사례다 [S1]. Pages 공식 게시 가이드의 검색 색인에서 Page 명의 게시 지원을 확인했으나 본문 접근은 실패했다 [S2]. 상세 권한·앱 심사·API 버전 지원은 운영 전 실제 앱 기준으로 검증한다.

Threads는 후속 확장 검토 대상이다. Meta 소유 Postman 자료가 검색되었지만 일부 직접 접근은 `Request not found`였다. 게시 한도 숫자나 상세 옵션은 확정 요구사항으로 사용하지 않는다 [S3].

## 3. 3인 역할 검토 결과와 통합 결정

| 논점 | 콘텐츠 편집장 | 플랫폼/API 담당 | 백엔드 운영 아키텍트 | 통합 설계 결정 |
|---|---|---|---|---|
| 성공 기준 | 새롭고 근거 있는 원고 | 스팸·참여 조작 방지 | 유효 원고의 안정 전달 | 발행 건수만으로 성공 평가 금지 |
| 빈도 | 초기 1건/일, 5건/주 | 안전 횟수 보장 불가 | 초기 최대 2건/일·4시간 간격 제안 | 신규는 1건/일·5건/주, Page 전체 2건/rolling 24h·4시간 간격 |
| 채널 | Facebook 집중 | Page와 개인 프로필 구분 | 어댑터 분리 | MVP Page 1개, Threads 후속 |
| 데이터 | 오래된 분위기를 현재로 서술 금지 | 사실·표현 책임 | 시점/근거 스냅샷 보존 | 생성·발행 직전 두 번 검증 |
| 카논 | 승인 설정만 사용 | 실제 경험 사칭 금지 | 본편 상태 불변 | 승인 캐릭터 텍스트 목록, 스토리 시계 진행 금지 |
| 자동화 | 초안 검수 후 유형별 자동화 | 공식 인증·제한 준수 | dry-run/live 분리 | 14일 이상·승인 샘플 10건 이상 검토 후 자동화 전환 판단 |
| 장애 | 부적격 글 보류 | 제한 시 채널 중지 | UNKNOWN 자동 재게시 금지 | 해당 글/채널 격리, 본편은 계속 실행 |

위 수치는 **내부 파일럿 제안값**이다. Meta의 허용량·권장 빈도·무차단 보장값이 아니다. 자동 증량은 MVP에서 제외한다. 빈도에 대한 두 역할의 차이는 신규 트랙 상한과 Page 전체 상한을 구분해 조정했다.

## 4. 범위

### 포함

- 기존 자료 읽기, 사용 가능한 근거/캐릭터 추출, 텍스트 원고 생성.
- 시장 관찰, 금융 개념 풀이, 발행된 에피소드 해설, 명시적 허구 캐릭터 대화.
- 사실·신선도·카논·중복 검사, 편집 승인, 예약 큐, 공식 Page 게시.
- 페이지 단위 통합 발행량 제어, 비용 상한, 결과 대사, 중단/정정 기록.
- 관리 기능은 초기 CLI/워크플로 입력과 보고서로 제공; 전용 웹 UI는 선택사항.

### 제외

- 개인 프로필·그룹 게시, Threads 실운영, 자동 댓글·좋아요·팔로우·DM.
- 이미지 신규 생성과 신규 캐릭터/관계/세계관 전개. 기존 이미지 재활용도 MVP 이후 검토.
- 시장 수집 주기의 고빈도화, 종목 매매 신호·수익 보장·실제 보유/거래 경험의 창작.
- X/본편 정책 전환, 운영 토큰 변경, 실제 게시·배포. 이번 요청의 산출물은 문서다.

## 6. 콘텐츠·빈도 정책 초안

| 설정 | 초기 제안 | 설명 |
|---|---|---|
| 신규 게시 상한 | KST 일 1건 / 월~일 주 5건 | 의무 수량 아님 |
| Page 전체 상한 | 최근 24시간 2건 | 기존 sidestory·신규·수동 게시까지 포함하는 운영 목표 |
| 최소 간격 | Page 전체 4시간 | 품질·독자 피로도 관리값 |
| 스케줄 | 평일 KST 18:30 슬롯 1개 | 외전 README의 화/목 10:17과 분리; 실제 지연 시 간격 재검사 |
| 놓친 슬롯 | 재고 몰아게시 금지 | 당일 유효 후보만 판단, 만료 시 폐기 |
| 후보 생성 | 슬롯당 후보 1개+수정 1회 | 상한/재료 검사를 생성보다 먼저 수행 |
| 원고 길이 | 본문 150~450자 지향 | 내부 편집값; 출처·기준시각 별도, API 최대길이와 구분 |
| 해시태그 | 기본 없음, 필요 시 관련 0~2개 | 반복·무관 태그와 참여 강요 금지 |
| 의미중복 검사 | 최근 30개 및 7일 주제 이력 | 임계값은 한국어 검증세트로 보정, 숫자 임의 확정 금지 |
| 생성 예산 | 일/월 금액 설정 필수 | 금액 미설정이면 유료 생성 비활성, 이전 프로젝트 예산 자동 상속 금지 |

수동 게시를 API로 완전하게 관측하지 못하면 Page 전체 상한을 엄밀히 보장할 수 없다. 운영자는 수동 게시를 같은 등록 절차로 기록하거나 해당 시간대를 차단해야 한다. 데이터 확인 불가 시 신규 자동 게시를 보류한다.

시장 자료는 단순 `24시간 미만`만으로 최신 판단하지 않는다. 거래소 달력과 가장 최근 완료 세션을 기준으로 검사한다. 휴일에는 마지막 세션 날짜를 명시한다. 일별 자료로 장중 시황을 생성하지 않는다. 실시간 기능은 별도 수집 SLA가 갖춰진 후 확장한다. 개념 설명은 시장 방향을 단정하지 않으며 승인된 개념 자료 버전을 사용한다.

캐릭터 텍스트의 구성은 ‘확인된 관찰 1개 → 의미 1개 → 짧은 창작 대사’로 한다. 캐릭터가 실제 투자자/운영자인 것처럼 거래·수익·현장 경험을 주장하지 않는다. 메타포가 실제 원인 분석으로 바뀌지 않도록 인과관계는 별도 근거가 있을 때만 쓴다. 예시 문장도 검증 데이터가 주입되기 전에는 발행할 수 없다.

## 7. 연결 설계

### 7.1 기존 기능을 활용하되 본편 경계 유지

`sidestory` 하위에 별도 `market_talk` 도메인·큐·진입점을 제안한다. 기존 8슬라이드 `run_publish()`에 텍스트를 억지로 넣지 않는다. Facebook 전송 어댑터의 message 게시 기능은 계약 검증 후 재사용할 수 있지만 기존 최근글 대사 동작은 그대로 복사하지 않는다.

본편 데이터는 기존 `icg_side.main_feed_*_v1` 읽기 전용 view 및 허용된 어댑터로만 읽는다. 필요한 컬럼이 view에 없으면 새 읽기 계약을 추가한다. `engine`/본편 `scripts`에서 sidestory 역참조를 만들지 않는다. 신규 글은 본편 episode 번호나 story/arc 진행 상태를 증가시키지 않는다.

기존 외전 README의 ‘본편 캐릭터를 그리지 않음’ 규칙은 유지한다. 신규 텍스트에 사용할 캐릭터는 별도 승인 목록을 정의한다. 기존 이미지 카논 규칙을 임의 해제하지 않는다.

### 7.2 처리 순서

1. 활성 여부·후보 생성 예산·Page 슬롯 잔여 확인.
2. 읽기 전용 근거/카논 스냅샷 및 최근 게시 이력 확보.
3. 새 정보 또는 승인된 개념 소재 선택. 없으면 정상 스킵.
4. 원고 생성→구조 검증→수치/단위/시점/카논/중복 검사.
5. 초안 검수 후 승인. 타입별 자동 승인 전환 전에는 수동 검수.
6. 게시 대기열 저장 및 예약. 발행 직전 근거·승인 버전 재확인.
7. 짧은 DB 트랜잭션에서 작업 선점과 Page 용량 예약.
8. 트랜잭션 종료 후 공식 API 전송. 외부 HTTP 동안 DB 락 유지 금지.
9. 외부 ID 확인→게시 영수증 저장. 불명확하면 UNKNOWN과 채널 발행 보류.
10. 모니터링·대사·필요 시 운영자 정정 처리.

### 7.3 상태와 복구

정상 상태: `PLANNED → GENERATED → VALIDATED → APPROVED → READY → CLAIMED → SENDING → PUBLISHED`.

| 상태 | 의미 | 재개 조건 |
|---|---|---|
| SKIPPED | 재료 없음/상한/시점 부적합 | 다음 슬롯에서 새 판단 |
| CONTENT_HOLD | 사실·카논·중복 검증 실패 | 수정·새 revision·재검증 |
| RETRY_WAIT | 부작용 없는 일시 실패 확정 | 횟수·기한·provider backoff 내에서만 재시도 |
| UNKNOWN | 이미 게시됐을 수 있음 | 외부 결과 확정 또는 운영자 확인; 자동 재POST 금지 |
| CHANNEL_HOLD | 인증·정책·한도 확인 필요 | 제한 해소 확인 및 운영자 재개 |
| DEAD_LETTER | 재시도 한도 초과 | 원인 해결 후 수동 재처리 |
| EXPIRED | 콘텐츠 유효기간 경과 | 재생성/재승인 없이 복구 금지 |

CLAIMED 임대 만료는 전송 의도 기록이 없을 때만 재선점할 수 있다. SENDING 이후 임대 만료는 UNKNOWN이다. 상태 전이는 claim token/version을 비교하여 오래된 작업자를 차단한다. 다만 DB fencing만으로 이미 진행 중인 HTTP 부작용을 취소할 수 없으므로 외부 exactly-once를 보장한다고 표현하지 않는다.

### 7.4 실제 코드에서 확인된 우선 보완점

1. `find_recent_post()`는 최근 10개만 메시지 일치로 검사한다. `run_publish()`는 대사 결과가 없으면 새 POST로 진행한다. 조회 지연·최근 범위 이탈이 있으면 중복 가능성이 있으므로 **UNKNOWN 미검색을 미발행 증거로 취급하지 않도록** 변경해야 한다. 실제 중복 장애가 확인된 것은 아니다.
2. 기존 sidestory dry-run은 publication/log 행을 쓰므로 신규 MT-16과 계약이 다르다. 신규 경로는 별도 구현하며 기존 dry-run 의미를 조용히 바꾸지 않는다.
3. 기존 `check()`는 Page ID/name 조회다. 읽기 성공만으로 게시 권한·앱 모드·심사를 충족한다고 판단하지 않는다.
4. 어댑터의 기본 API 버전 문자열/출시일 주석은 코드 사실일 뿐 공식 지원 검증이 아니다. 운영 전 공식 지원 버전과 실제 앱 호환성을 확인한다.
5. 신규/기존 외전이 같은 Page이면 양쪽이 공통 용량 예약을 사용해야 한다. 신규 쪽에서만 제한하면 통합 상한을 보장할 수 없다.

## 8. 논리 데이터·보안 요구

아래는 신규 설계이며 현재 DB에 존재한다고 확인한 테이블이 아니다. 구체 DDL은 구현 단계 산출물로 분리한다.

| 논리 엔티티 | 핵심 데이터/제약 |
|---|---|
| talk_items | UUID, 업무키, 유형, topic/claim/evidence hash, 본문 hash, revision, canon_version, source_refs, observed_at, expires_at, 상태, 승인자/시각 |
| talk_outbox | item_revision+channel+account_id unique, due_at, claim_token, lease_until, attempt_count, send_started_at |
| talk_attempts | 요청 식별자, payload hash, 시작/종료시각, HTTP/플랫폼 코드, 결과 확실성, 외부 post_id |
| talk_receipts | channel+account_id+post_id unique, published_at, permalink, 확인시각 |
| channel_reservations | Page/시간창별 게시 예약, 기존/신규 트랙, UNKNOWN 용량 유지, 정책 버전 |
| talk_cost_ledger | 모델/요청/예약비용/실제비용, 일·월 합계, 불명확 청구 상태 |
| talk_audit | 승인/변경/보류/정정/재개 주체·이유·시각 |

큐는 `(status, due_at)` 조회 인덱스, 이력은 `(account_id, published_at)` 기준 조회를 설계한다. 기존 본편 테이블에 반복 UPDATE하지 않는다. 트랜잭션 선점·한도 예약은 서버 측 하나의 원자적 연산으로 구현하고 클라이언트의 조회→갱신 두 호출로 대체하지 않는다.

노출 스키마의 신규 테이블에는 RLS와 최소 권한을 적용한다. 본편 view 읽기 권한과 신규 테이블 쓰기 권한을 분리한다. 기존 SUPABASE_KEY의 권한 수준은 이번에 확인하지 않았으며, 강한 키 사용만으로 읽기 전용 격리가 달성된다고 보지 않는다. 운영 로그에는 토큰·인증 헤더·비밀 쿼리 문자열을 저장하지 않는다. 계정 권한·보관 기간은 운영 설정으로 확정한다.

## 11. 운영 지표와 도입 순서

지표 정의: 검증 통과율=검증 통과 후보/전체 검증 후보, 발행 성공률=확정 게시/실제 전송 시작 건, 사실 오류율=오류 확인 게시/검토한 게시, 중복률=확인된 중복 게시/확정 게시. UNKNOWN은 성공·명확한 실패와 별도 집계한다. 신규 정보 부족으로 SKIPPED한 건은 발행 실패 분모에 넣지 않는다. 건당 비용은 실패·재생성 비용을 포함한다.

조회 가능한 도달·반응 지표는 보조성과로 사용한다. 숨김/신고/노출 데이터가 API에 없으면 수집한다고 약속하지 않는다. 계정 경고가 관측되지 않았다는 사실은 제한이 없다는 보장이 아니다.

1. 구현 전 HEAD·실제 카논·읽기 view·Page 계정·앱 권한·현재 외전 설정을 확인한다.
2. 신규 경로 개발·단위/계약/동시성/장애/회귀 시험을 수행한다. 운영 기능 기본값은 비활성이다.
3. 최소 14일 동안 초안 검토, 최소 10개 원고 승인 샘플을 확보한다. 사실·카논 오류가 있으면 수정하고 검증을 반복한다.
4. 별도 운영 승인 후 Page에 감독하 테스트 게시를 수행하고 permalink와 중복 여부를 확인한다.
5. 승인된 콘텐츠 유형부터 일 1건·주5건 상한으로 자동화한다. 14일 이상 운영 자료를 보고 유지·감량·증량을 판단한다. 증가폭은 검증 결과를 보고 별도 결정한다.
6. 중단 시 신규 스케줄/발행을 끄고 원장·UNKNOWN·기존 게시물은 보존한다. 자동 삭제/재게시로 롤백하지 않는다.

운영 전 미확정 항목: 실제 Page ID, 사용자 관리 권한, 앱 심사/모드와 필요 권한, 공식 API 지원 버전/제한/비용, 기존 외전 활성 여부, 캐릭터 텍스트 허용목록, 일/월 생성예산, 알림 채널, 이력 보관기간. 이 항목은 문서 작성의 장애물이 아니라 live 활성화 전 필수 확인사항이다.
